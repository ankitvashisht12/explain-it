One helper read the live settings instead of the job's pinned photocopy. Jobs that spanned a release came out half-old and half-new — and only on the days someone pressed Release at the wrong moment.

Runner · step execution

When does this code even run?

Runnerwakes at 02:00, starts the nightly invoice job, and pins it: job.pinnedRelease = 13.
Runnerwalks the job's steps one at a time by calling runStep — the hottest path in the service, roughly 40,000 calls an hour.
One tiny job inside itbefore each step, fetch the settings that tell it where to send output — which is where the wrong copy got read.

The window is small and entirely invisible in testing: it only opens when someone presses Release while a job is already mid-flight. On weekdays that is most of the afternoon.

Problem

What's wrong

Two ways to read settings had grown side by side. loadRelease(version) reads a specific photocopy. currentConfig() reads whatever is live right now — the correct thing to call from the dashboard, and the wrong thing to call from anywhere inside a running job.

runStep called currentConfig(). Steps that ran before the release used version 13; steps after it silently used 14.

⚠
Cost, concretely: the nightly invoice job runs about twenty minutes across ~2,400 steps. A release landing mid-run splits it: invoices already generated carry the old billing address, the rest carry the new one, and nothing in the logs marks the seam. Three support tickets in two months traced back to this, each taking a day to reproduce because reproducing it means pressing Release at exactly the right second.
Fix

The fix

The step runner already knows the pin. It just wasn't using it:

Read the pinned photocopy, not the live settings runner/src/steps.ts (~line 88)
  async function runStep(job, step) {-   const config = await currentConfig(job.tenantId)   // live settings — changes under a running job+   const config = await loadRelease(job.pinnedRelease) // the photocopy this job was pinned to at 02:00    return dispatch(step, config)  }

One line, but the same mistake was reachable from four other call sites. So the loophole was closed as well as the leak: currentConfig now refuses to answer inside a job context, which turns a silent wrong answer into a loud failure at the moment of the mistake.

Make the wrong call impossible instead of merely fixed runner/src/config.ts (~line 24)
  export async function currentConfig(tenantId) {+   if (runContext.active())                            // inside a job, "current" is never the right answer+     throw new Error("use loadRelease(job.pinnedRelease) inside a job")    return db.settings.findOne({ tenantId })  }
✓
Why it's safe: outside a job — the dashboard, the release preview, the settings API — runContext.active() is false and behaviour is byte-identical. Inside a job the old behaviour was already incorrect, so nothing worth preserving is being broken. The three remaining call sites were audited: all of them are dashboard reads.
