Overview

What it produces

A folder of plain HTML files. Every page is self-contained — all CSS inline, no router, no bundler, no network calls beyond one web-font link — so the site opens straight from disk, survives being zipped into an email, and still works in five years.

  • A root primer that gives the reader the minimum mental model in about two minutes, then links to every topic page.
  • One page per topic — a change, a bug, a decision, a subsystem. Three to seven is the sweet spot; beyond nine, topics get merged rather than added.
  • A shared sidebar, repeated in every page with the current entry marked, collapsible to a rail when it is in the way.
  • A scoreboard closing the primer: every item on the site with its status and its location in the codebase.
💡
Who it is aimed at: the reader is a capable engineer who has never seen this repository. They can follow any concept that gets explained and zero concepts that don't. Everything below follows from calibrating to exactly that person — never talking down, never assuming repo knowledge.
Method

How it writes

Read the code first, always

Nothing gets explained from memory of a conversation. For each topic the skill reads the changed lines, the enclosing function, and at least one caller — enough to answer "when does this code even run?" with a true story rather than a plausible one. A claim that came from a review comment gets verified against the source before it is repeated.

Ground every page in a runtime moment

Abstract code turns concrete the second a reader can picture the moment it fires. Every topic page opens with two to four actor beats — who does what, ending in the one small job the page is about. Real function names ride alongside the plain-language story, never instead of it.

One metaphor per concept, reused verbatim

A metaphor is introduced once, in the primer, in bold — then used with the same word everywhere after. "Photocopy" never quietly becomes "snapshot" two pages later. Metaphors also have to be mechanically faithful: they must not break under the exact behaviour being explained.

Show the change, quantify the reason

Changes appear as trimmed red/green diffs of real code with the file path in the header and inline comments pointing at why, not narrating what. Vague quantifiers are banned outright — "slow" gets replaced by the number, the size, or the concrete triggering input. And a defensible product choice is presented as a decision with its trade-off, never dressed up as a defect.

The worked example: Lantern

The two topic pages explain a change in Lantern, a scheduled-job runner. Lantern is invented for this demo — there is no such repository, and every identifier below is fictional. What is real is the shape: this is what the skill's own primer section looks like when it is doing its job.

Lantern runs recurring jobs — nightly imports, invoice runs, digest emails. What a job actually does is defined by a bundle of settings its owner edits in a web dashboard (internally, a config).

Settings are edited constantly, but jobs must not change shape halfway through a run. So Lantern separates editing from running: pressing Release takes a photocopy of the settings exactly as they are, stored as a new row in releases with the frozen bundle in releases.configBlob. Editing afterwards changes the live settings and never touches the photocopy.

Every job that starts gets a sticky note — a pin — recording which photocopy it belongs to: job.pinnedRelease = 13. From then on the pin is the job's whole world.

Owneredits the settings freely, all day. Nothing running is affected.
Ownerpresses Release — a photocopy is taken and becomes version 13.
Runnerstarts a job at 02:00, pins it to version 13, and works through its steps for the next twenty minutes.

Which gives the rule both topic pages revolve around:

✓
The invariant: a running job must only ever read its pinned photocopy — never the live settings, never a newer release.

Page 01 is what happens when one code path forgets that rule. Page 02 is about the cost of obeying it naively.
