Stop loading the whole photocopy
on every dashboard poll

Reading from the pinned release is correct. Reading all of it, five times a minute, to answer a question that is almost always "nothing changed", is not.

API · dashboard polling

When does this code even run?

Ownerleaves the Lantern dashboard open on a second monitor — the normal way the product gets used.
Browserpolls /api/jobs/live every five seconds so the run list stays fresh.
Serverruns handleRequest, and for each running job loads that job's photocopy to render which steps it is made of.
Problem

What's wrong

A photocopy is one row, but a fat one: releases.configBlob holds the full settings bundle — every step, every template, every credential reference — and averages 180 KB, with the largest tenant at 2.1 MB. The dashboard needs roughly forty bytes of it: the release version, to decide whether the run list it already has is still accurate.

⚠
Cost, concretely: one open dashboard with 12 running jobs pulls ~2.2 MB out of the database every five seconds — 1.5 GB an hour, per open tab. Roughly 99% of those reads answer "same version as last time, nothing to redraw". During business hours this single endpoint accounted for 61% of read traffic on the primary.
Fix

The fix

Ask the cheap question first. The version number lives on the job row that is already in memory, so the expensive read only happens when the answer can actually differ from what the browser has:

Version check before blob read api/src/dashboard.ts (~line 140)
  async function liveJobs(req) {    const jobs = await db.jobs.running(req.tenantId)-   const shapes = await Promise.all(-     jobs.map(j => loadRelease(j.pinnedRelease))     // ~180 KB each, every 5 seconds-   )+   const seen = req.query.seenVersions ?? {}          // what the browser already holds+   const stale = jobs.filter(j => seen[j.id] !== j.pinnedRelease)+   const shapes = await Promise.all(                   // free in-memory check, no DB read+     stale.map(j => loadRelease(j.pinnedRelease))+   )    return render(jobs, shapes)  }

The browser sends back the versions it already has; the server only re-sends shapes that changed. Steady-state polling now reads zero blobs, and a release causes exactly one blob read per affected job.

✓
Why it's safe: the pin is immutable for a job's lifetime and a photocopy is immutable once taken, so "same version" genuinely implies "same bytes" — the check cannot go stale in the way a cache can. A browser that sends no seenVersions (first load, hard refresh, old client) gets the previous full-fetch behaviour.
🤔
Decision, not a bug: owners regularly ask why edits don't show up in a job they are watching. That is the pinned-photocopy invariant working exactly as designed, not a staleness bug — but it is also a real confusion, and the honest fix is a product one: label the run list with the version each job is pinned to, so "why isn't my edit here" answers itself. That is a call for whoever owns the dashboard, not a fix to make quietly in the API.
